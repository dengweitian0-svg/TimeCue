# internal/runtime

- 本目录负责承载应用运行单元；具体业务组件应通过明确接口接入，不得把进程级启动职责下沉到这里。
- 当前文件：
  - `runtime.go`：定义当前最小运行实现 `IdleApplication`。
- `IdleApplication.Run` 接收 bootstrap 注入的 `Store`，持续等待 `context` 取消并返回 `ctx.Err()`；`context.Canceled` 由 `bootstrap` 识别为正常退出。
- 运行单元通过 `bootstrap.Application` 接收配置、logger 和 Store；不得自行加载配置、创建全局日志器、决定进程退出码或关闭顶层资源。Store 的所有权仍归 bootstrap。
- 运行时组装边界负责创建并共享 `MutationCoordinator`、`ReminderScheduler` 与业务 `Service`，将生命周期/时间环境适配器的 `RuntimeEvent` 回流到调度器；不得绕过协调器直接修改候选、epoch 或日程事实。#14 负责在该边界接入 Wails、Windows 电源/时钟事件、真实通知和资源逆序关闭，本 Issue 不实现这些平台适配。
- 运行时的窗口可见状态与调度生命周期状态分离；`running`、`suspended`、`stopping` 只由调度契约表达。停止时先关闭业务写入和提醒派发资格，再由顶层按资源所有权完成取消和释放。
- 新增 UI、调度、存储或领域逻辑时必须拆分为职责独立的组件，通过窄接口接入运行时，并保持可测试性。
- 运行循环、状态变化、并发控制和外部副作用必须有准确的中文注释、必要日志和对应测试。
- `DesktopApplication` 只从 `bootstrap.Store` 一次性取得 `DesktopStore` 组合端口，并在运行时内共享唯一 `Service`、`MutationCoordinator`、`ReminderScheduler`；Store 的关闭责任仍归 bootstrap。
- `DesktopDependencies` 通过 `platform.DirectoryAccess` 和 `platform.DirectoryChooser` 接入目录设置；Runtime 绑定只协调验证和配置保存，不直接操作配置文件或替换 bootstrap 持有的 logger、SQLite Store。
- `WailsBindings` 是平台无关的强类型边界，所有前端输出必须带 `json` tag；写入继续经过 Service/Coordinator，停止阶段返回 `RUNTIME_STOPPING`。
- 配置绑定通过 `GetLogLevel`、`SaveLogLevel`、`GetTheme`、`SaveTheme` 和 `RestoreConfigDefault` 暴露受限配置属性；日志级别、日志路径和备份路径保存后重启生效，窗口关闭行为和主题保存后立即生效。Runtime 不直接操作 YAML 文件，统一调用 `config.Config` 的正式保存转换。
- 配置文件写入失败统一包装为 `ConfigPersistenceError`，必须保留 cause 链并由 `ErrorFormatter` 映射为 `STORAGE`；不要让前端依赖底层文件路径或具体存储错误类型。
- Issue #31 的提醒边界由 `ListPendingReminders`、`GetReminderDetail(schedule_id, original_date)` 和 `ConfirmReminder(schedule_id, original_date)` 组成。查询只读当前事实；详情正文不可重建时必须返回可观察状态和可空正文，不得从当前空值伪造历史内容。确认必须经过唯一 Service、MutationCoordinator 和 SQLite 事务，只有事务提交成功后才允许前端移除待处理项。
- Issue #49 的恢复状态通过 `SchedulerStatus.RecoveryStatus` 和 `FrontendEventRecovery` 独立暴露；前端未 ready 时 runtime 必须保留最新恢复事件，前端 ready 后补发，恢复完成事件只能发生在最终 checkpoint 提交成功之后。
- 提醒状态转换保持单向：`submitted + processed_at_utc IS NULL → pending → confirmed`；缺失、`claimed`、`failed`、`skipped` 等状态分别映射为 `missing` 或 `not_processable`，不能被确认绑定伪装成成功。重复确认返回首次处理时间且不产生第二次写入；目标不存在、不可处理、底层失败和 `stopping` 必须保留现有错误分类及 `ErrorFormatter` 行为。
- 通知页面的稳定身份是 `schedule_id + original_date`，不是列表索引或标题。前端通过 `sequence` 去重、通过 `FrontendReady(last_sequence)` 接收前端未就绪期间保留的最新激活；激活只负责显示、切页和定位，不自动确认。逐条 Toast、退出后不冷启动、不自动确认和确认后优先同刻下一条是 Issue #31 的固定决定。
- Windows 验收必须分开记录四件事：通知端口接收、系统实际显示、点击定位/现有窗口激活、确认持久化。fake 平台测试只能证明端口和状态转换，不能替代 Windows 通知中心观察；构建前还需执行前端检查、Go 检查及 `wails build -platform windows/amd64 -webview2 embed`。
- `GetStorageDirectories` 返回每类目录的 `effective_path`、`saved_path` 和 `restart_required`；effective 来自启动时冻结的 `ResolvedPaths`，saved 来自 `config.yaml`。`SaveStorageDirectory` 仅在 `running` 状态执行，成功后明确提示重启生效，失败不覆盖前端输入或当前生效值。
- 激活事件使用单调 sequence 和 `FrontendReady(last_sequence)` 握手；前端未就绪时只保留最新激活，发送失败不得静默丢弃。
- 停止必须先使 scheduler/协调器进入 `stopping`，再取消并等待 scheduler。系统通知历史清理是退出前的尽力操作：失败只记录一次可定位告警，不能阻断事件源、托盘、通知资源和宿主窗口的关闭；托盘退出即使其他桌面资源关闭失败也必须请求宿主关闭窗口，避免遗留半退出界面。非终止路径的资源关闭失败进入 `cleanup_failed` 并允许 `RetryCleanup`。启动后的前端状态只以 SQLite 与调度恢复结果为准，遗留 Toast 不构成提醒事实。runtime 不关闭 bootstrap Store。
