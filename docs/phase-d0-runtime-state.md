# D0：运行状态保存边界

任务分组、展示次数、尝试成员和恢复位置继续只保存在运行内存中；预加载状态按最新 D1 方案复用 `notifications.status=loaded` 保存。仍不新增运行状态表、字段、runtime_json 或 RuntimeStore，不引入租约和心跳。

当前代码与数据库要求仍为版本 2。D1 直接修改现有 `001_initial.up.sql` 的 status CHECK 支持 loaded，不新增迁移或中间表。D1 已实现，详见[D1 分钟调度方案](phase-d1-minute-scheduler.md)；旧库不会因 SQL 文件修改而自动变化。

## 保存边界

日程规则、每次提醒的计划时间、加载/投递当前状态、确认时间、历史文本、规则版本及永久停止标记继续保存到原有数据库。status 使用 pending/loaded/sent/failed；failed 重加载后变为 loaded，上一失败及预算只保存在本次运行内存，不承诺跨重启的尝试历史。

任务分组、展示次数、当前尝试及其成员、生成位置和恢复整理进度只在本次 Go 运行的内存中记录。Go 重启后重新建立，不要求累计此前运行的展示次数，不恢复旧尝试或回执日志。

阶段 D 使用单个 Flutter 通知执行者，不引入执行租约或周期性心跳。失败优先根据明确的执行结果和进程退出事件处理，不建设多执行者协调机制。

## 后续接入

D0 确定上述保存边界，不提前实现独立运行状态模型。D1 每 30 秒扫描前后各 30 秒窗口，提交后的未来 1 分钟首提醒即时入队；D2 在实际使用处维护展示计数、队列及尝试；D3 在内存维护恢复终点和当前位置，重启重新扫描，复用原提醒唯一键去重。

四次展示及 5/30/120 秒重试等待只约束本次 Go 运行。已记录 sent 或已确认、永久停止的提醒继续按原业务状态筛选；平台已展示但尚未回填时崩溃，重启后允许再次展示。

数据库 loaded 不能证明任务已进入当前内存。Go 重启后按计划时间重新加载、核验或交恢复，不能跳过旧 loaded，也不恢复旧 attempt。实际到期先冻结文本再开放完整分组，平台接受展示后才记录 sent。

D1 已实现，D2–D4 及 Windows 通知仍待接入。D1 的 loaded 扩展现有查询的 deliveryStatus 枚举，须通过 Apifox 再开展 Flutter 状态适配。
